# ADR-005 페이지 경계 청킹·tiktoken 기준

- 상태: 채택
- 날짜: 2026-11-12
- 관련: 설계서 5.3, `apps/api/app/documents/{parser,normalize,chunker}.py`

## 맥락

인용은 "문서 + PDF 물리 페이지"로 보여 준다. 청크가 페이지를 넘으면 근거 카드의 페이지 번호가 모호해지고, 평가(page Hit@k)도 흔들린다. 임베딩 모델을 바꿔도 청킹 결과는 같아야 재색인·평가 비교가 된다.

## 결정

- 파서 `pymupdf-v1`: `page.get_text("text")`만 쓴다(링크·스크립트·주석 미처리). 암호 PDF `encrypted_pdf`, 페이지 상한 `too_many_pages`, 60초 상한 `parse_timeout`. 공백 제외 5자 이상인 페이지를 "텍스트 있음"으로 보고, 그 비율이 20% 미만이면 `unsupported_scan`.
- 정규화: NFC → `\r\n`/`\r`→`\n`, 탭→공백 → 제어 문자 제거(줄바꿈 제외) → 줄 끝 공백 제거, 3개 이상 줄바꿈→2개. 반복 헤더/푸터 제거는 **검증 전 미적용**(슬라이드 제목이 반복 헤더처럼 보이는 경우가 많아 오히려 근거를 지울 위험).
- 청커 `v1`: tiktoken `cl100k_base`, target 400 / overlap 60 / max 600 / min 20 토큰. 페이지 단위로만 자른다.
  - 페이지 ≤ 600 토큰이면 1청크.
  - 아니면 문단(빈 줄) → 문장(`. ` `? ` `! ` 뒤 공백, 줄바꿈) → 토큰 강제 분할 순으로 단위를 만들고, 누적해 400을 넘기 직전에 끊는다.
  - 다음 청크는 이전 청크 끝 60토큰 지점부터 시작한다(원문 오프셋 기준이라 `char_start/char_end`가 정확하다). overlap을 붙이면 600을 넘는 경우는 overlap을 생략한다.
  - 페이지 마지막 청크의 새 내용이 20토큰 미만이면 600 안에서 직전 청크에 합친다. 페이지 자체가 짧으면 20토큰 미만이라도 1청크(빈 페이지는 0청크).
- `chunk_id = uuid5(6f0c2c3e-5d0b-4e4b-9a2d-3b0c1b4d9e11, "doc:ver:page:ordinal")`. 같은 값을 Qdrant point ID와 OpenSearch `_id`로 쓴다.

## 설계서와 다른 점

- 설계서 문장 경계 목록의 `다. `는 `. ` 패턴에 포함되므로 별도 규칙을 두지 않았다.
- 설계서 M3의 `EMBEDDING_PROVIDER=none` 임시 허용은 쓰지 않았다. M3 동안 임베딩·색인 단계는 코드상 no-op이었고 M4에서 바로 채웠다.

## 결과

- 단위 테스트(`tests/unit/test_chunking.py`): 페이지 경계 불침범, 모든 청크 ≤ 600, overlap 길이, 짧은 페이지 1청크·빈 페이지 0청크, chunk_id 결정성, 파서 페이지 매핑.
- 한국어는 cl100k에서 글자당 토큰이 많아(대략 1글자 ≈ 1토큰 안팎) 슬라이드 한 장은 대부분 1청크가 된다. 실제 분포는 M9 평가 때 기록한다.
